# mergegate — tech stack & architecture

Status: draft v0.1 · 2026-10-13 · companion to [design.md](design.md)

## 1. Drivers

- **The CLI and UI must be lightning fast.** Agents call `mg` constantly, so startup time and output size (tokens) matter. The UI must never wait on computation.
- **Agents maintain the codebase.** We choose for outcome quality and runtime speed, not for human ergonomics. Strict compilers and enforced boundaries beat conventions written in a README.
- **Pluggable parts.** Every slice sits behind an interface and can be swapped or extended without touching the others.

The principle behind most choices below: **precompute at submit time, display at review time.** Diffs and highlighting are computed once and cached by blob. Tiers are computed per revision and recomputed for open items when the rules change, so they are keyed by rules version too. Opening an item is a database read.

## 2. Decisions

| # | Question | Decision |
|---|---|---|
| 1 | Language | Rust. One binary for hub and CLI. |
| 2 | UI | Web UI served by the hub. A native shell (WKWebView) or PWA install can come later without a second UI. |
| 3 | Syntax highlighting | Server-side tree-sitter, cached per blob. Grammars are optional per-language downloads (§6). |
| 4 | Git | Split: gitoxide for reads, the `git` binary for writes and anything that must match git exactly (§5). |
| 5 | Config format | TOML for files the operator edits by hand (`rules.toml`, `hub.toml`). Project settings live in the database and change only through `mg project set`, which validates them and re-syncs what depends on them. YAML breaks on unquoted globs (`**/*.swift` is an alias) and Rust's YAML crates are unmaintained or forked. |
| 6 | Agent surface | Self-describing CLI + one skill embedded in the binary + `mg resume` prompt. No MCP server (§8). |

## 3. Stack

| Layer | Choice | Notes |
|---|---|---|
| Hub + CLI | Rust, single binary `mg` | ~1 ms startup, no GC. `mg hub start` launches the daemon; every other command, `mg hub` admin commands included, is a client of it. |
| HTTP | axum + tokio | API, long-poll `mg wait`, SSE for the UI, git smart-HTTP. |
| CLI | clap; blocking HTTP client | Output contract (`--json`, exit codes, `needs_decision`) lives in one module. |
| Storage | SQLite, WAL (rusqlite) | Event log is an append-only table; its rowid is the `mg wait` cursor. Attachments stored on disk by sha256 (`sha2`), under `$MERGEGATE_HOME/attachments/`, and served with single-range support written by hand (video seeking needs it; `tower-http`'s `ServeFile` would add a dependency for one route). |
| Git reads | gitoxide (`gix`) + imara-diff | Blob/tree reads, tree diffs, rev walks, line mapping for comment anchoring. |
| Git writes | `git` ≥ 2.40 subprocess | `http-backend` (receive), `merge-tree --write-tree`, `check-attr --source`, push upstream, `updateInstead`. Run with a sanitized environment (§5). |
| GitHub | ureq (blocking, rustls) with typed endpoints, ETag-conditional polling | Token from `gh auth token`, in memory only; git gets it as an `http.<url>.extraheader` through `GIT_CONFIG_*` variables. No octocrab, no tokio in the adapter: the hub calls it from `spawn_blocking`, as it does git. `MG_GITHUB_API_URL` and `MG_GITHUB_URL` point it elsewhere, for the fake; `MG_GITHUB_POLL_MS`, `MG_EXTERNAL_QUIET_MS` and `MG_EXTERNAL_CAP_MS` shorten the comment poll and batching for tests. |
| Highlighting | tree-sitter, grammars loaded as WASM at runtime | See §6. |
| Tailscale | The `tailscale` CLI: `status --json` and `whois --json`, each peer's answer cached | No Go client library in Rust, and the macOS app exposes the LocalAPI differently from Linux; the CLI answers the same on both, in about 25 ms. Found on `PATH`, else inside the Mac app. |
| UI | SolidJS + TypeScript, esbuild with `esbuild-plugin-solid`, pnpm; embedded in the binary | Fine-grained reactivity, no virtual DOM, ~7 KB runtime. The hub's `build.rs` builds it, so a plain `cargo build` yields a binary with the UI; without pnpm it embeds a stub page that `mg doctor` reports, and `MG_REQUIRE_UI=1` makes that an error. ESLint with `eslint-plugin-solid` lints, Biome only formats. |
| Diff view | `@pierre/diffs` `CodeView` (Apache-2.0), wrapped in `ui/diff-view/` | Variable-height virtualization, scroll anchoring, sticky file headers, line selection, expandable context, annotation slots for comments. It's fed the hunks the hub computed, so it shows exactly the lines comments anchor to, and the hub's spans paint them (§6); `ui/build.mjs` leaves Shiki's grammars and themes out. Its rows use inline styles, so the hub's CSP allows them. Cmd+F can't find lines scrolled out of view. |
| UI styling | Own design tokens (CSS custom properties) + small primitive set | No Tailwind, no component library. Tokens are copied by hand from the Academy Figma; features use only its semantic names. DM Sans, self-hosted. |
| API contract | Rust types are the source of truth; TS types generated by ts-rs (`pnpm gen`, gitignored) | CLI, hub and UI cannot drift. |
| Packaging | GitHub releases signed with [packslip](https://packslip.dev), installed and upgraded with mise (`packslip:damian-kolasinski/mergegate`) | A tag runs `release.yml`, which builds mg for macOS and Linux on arm64 and x86_64 (Linux on Ubuntu 22.04, so it needs glibc 2.35 or newer) and signs the archives keylessly from the workflow, so mise checks who built a release before installing it. The repository is public, so installing needs no credentials. No Homebrew tap or installer script of our own, and no `mg self-update`: mise owns upgrades. `mg hub start` installs and loads a launchd agent / systemd user unit for the default home, so the hub starts at login and after a crash; `mg hub stop` removes it. With `MERGEGATE_HOME` set, or no usable manager, it starts the hub detached instead. |

## 4. Architecture: ports and adapters

```
crates/
  core/                  domain: item state machine, revisions, events, triage policy,
                         inbox ordering, comment anchoring. No I/O dependencies.
  api/                   wire types (serde + generated TS)
  git/                   Git port impl: gix reads + git-cli writes
  backend-github/
  backend-local/
  store-sqlite/
  rules-toml/            RulesFile port impl: reads and writes the operator's rules.toml
  highlight/             tree-sitter + WASM grammar loader + language manager
  judge-jev/             Judge port impl: TypeSafe AI's Jev over HTTP
  judge-command/         Judge port impl: the operator's command, JSON over stdio
  tailscale/             Tailnet port impl: the tailscale CLI
  hub/                   axum server, scheduler, wake runner; composition root of the daemon
  cli/                   mg commands
  skill/                 SKILL.md + references, embedded
  testkit/               test harness: real hub, git repos and mg binaries in temp dirs
ui/
  app/                   entry point, routing, hub client, keyboard map
  design-system/         tokens, primitives
  inbox/  item/  rules/  one directory per screen
  diff-view/             wraps @pierre/diffs' CodeView; fed the hub's hunks
  tests/                 Playwright against the real hub
langs/                   language pack builder: pinned grammars, queries, build.mjs
```

Ports (traits in `core`): `Git`, `Backend`, `Store`, `RulesFile`, `Highlighter`, `Judge`, `FileRanker`, `ItemRanker`, `Auth`, `Clock`.

- **The lasting layout and boundary rules live in the `architecture` skill** (`.claude/skills/architecture`). Slice-specific decisions stay in this doc until the slice is implemented; after that the code is the reference and the section can be removed.
- **Boundaries are enforced by the crate graph.** `core` may not depend on I/O crates or on any other workspace crate, `api` included; a test in CI (`crates/testkit/tests/boundaries.rs`) fails the build if it does. `core` has its own domain types; `hub` and `cli` map them to the wire types in `api`. Adapters depend on `core` and `api` only, never on each other.
- **Three ways to plug in:**
  - runtime, per project, via config: backend, judge;
  - build time via cargo features: optional adapters;
  - out of process via JSON over stdio: judge `command` today, third-party backends later.

## 5. Git split

| Operation | Implementation | Why |
|---|---|---|
| Receive pushes from workers | `git http-backend` (CGI) behind axum, bodies streamed both ways, `refs/mergegate` hidden | gix has no server side. |
| Test-merge, merge | `git merge-tree --write-tree` | Must match git's `ort` merge exactly, or conflicts are detected wrongly. The early watch reuses it: each pair of open items is merged again only when one of their heads moved, and each item against a target commit only once per hub run (once per revision across restarts, as a conflict already sent isn't tried again). Every pass, a submit's or a merge's too, re-fetches each target. `MG_TARGET_POLL_MS` shortens the target poll for tests, and `MG_TARGET_WATCH=off` stops the watch for tests of what a merge finds. |
| Push to GitHub / operator repo | `git push` (`updateInstead` for local) | gix push is incomplete; must respect git semantics. |
| Read blobs, trees, history | gix | No process spawn per call (~2–5 ms each on macOS); typed results. |
| File diffs, interdiffs | gix tree diff + imara-diff (histogram) | In-memory; yields the line mapping that comment anchoring needs. |

Everything goes through the single `Git` port, so any operation can move between gix and the `git` binary without callers changing. Subprocess calls on the hub's own repos run with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, an isolated `HOME` and `XDG_CONFIG_HOME`, explicit `-c` overrides and hooks disabled, so the operator's personal git config can't change output.

The `local` backend's push into the operator's repo is the exception. The receiving side runs in that repo, so its config and hooks apply, which is intended because it's the operator's repo. `-c` overrides don't reach a local `receive-pack`, so the hub passes `--receive-pack="git -c receive.denyCurrentBranch=updateInstead receive-pack"` instead of changing the operator's repo config.

**Interdiff after the base moved.** If the target advanced between r1 and r2, a raw r1→r2 diff includes upstream changes. The hub replays r1 onto r2's base (`git merge-tree --write-tree --merge-base=<r1 base> <r2 base> <r1 head>`) and diffs that tree against r2's head, so only the item's own changes show; with an unmoved base it diffs head against head. A file the replay conflicts on shows its whole own diff in r2. Each replayed tree is pinned under the item's refs until the item closes, and interdiff file diffs share the blob-pair cache.

**Comments are placed on read.** Opening an item, and rereading its conversation onto the revision on screen (`?onto=`), diffs each commented file between the comment's revision and that one, reusing the blob-pair cache, and maps the comment's lines through the hunks. Nothing is stored, so a comment written on an old revision or ingested late needs no write path of its own. It's the one exception to request paths only reading, kept because it's cheap: in `open_item_budget` (release build), an item with 60 comments over twenty 300-line files on a rebased revision opens in 2.0 ms against 0.4 ms without comments, about 80 µs a file, and about 190 µs a file at 3,000 lines. Submitting or approving moves the drafts that can move, and a draft is re-placed by rewriting its anchor.

## 6. Syntax highlighting and language packs

The hub parses the full old and new blob with tree-sitter, in a background task woken by submits and `mg lang add`: it highlights the blobs of every open item's newest revision that lack spans for an installed grammar, so the submit request doesn't wait on it and a file opened before then shows plain until the next load. It stores per-line token spans (`[start, len, class]`, columns in UTF-16 units as the browser counts them) in SQLite keyed by blob, grammar and a version covering every installed pack's archive digest and mg's span format, since injections reach across packs: adding, removing or reinstalling any pack highlights open items again and drops the stale rows. Spans are pruned with the diffs when an item closes. The same parse feeds structural triage signals (§7).

Hunks carry their lines' spans in `GET /api/items/{id}`; expanding a gap reads the whole blob's spans from `GET /api/highlights/{grammar}/{blob}`. Classes are a fixed set mapped from capture names (keyword, string, comment, function, type, …). The UI paints them into CodeView by wrapping its renderer's highlight step, the one place that sees each line's side and number; it's private to `@pierre/diffs`, and `ui/tests/highlight.spec.ts` fails if an upgrade moves it. They're coloured with Pierre's light and dark theme colours, so a highlighted file looks as Shiki would show it.

**Languages are optional downloads, managed per hub.** Only the hub highlights, so workers never need grammars and `mg` itself ships with none.

A language pack is a gzipped tar of `pack.json` (name, version, grammars with their file extensions, file names and query files) and, per grammar:
- the grammar compiled to WASM: one file for every OS/arch, sandboxed, no native code loaded;
- the tree-sitter queries `highlights.scm` (plus `injections.scm` and `locals.scm` where present). Injections reach across installed packs, so fenced code in Markdown and `<script>` in HTML are highlighted.

Packs are built from pinned npm releases (`langs/packs.json`, by version and integrity) with a pinned tree-sitter CLI (`tree-sitter build --wasm`), never taken prebuilt, so every grammar has the runtime's ABI. `langs/build.mjs` writes one `<name>-<version>.tar.gz` each; CI builds them all, loads every one, and keeps them as the `language-packs` artifact. The first set: rust, typescript (with tsx), javascript, json, toml, markdown (with its inline grammar), css, html, bash, yaml, python, go, swift, kotlin, elixir. None is bundled.

Grammars load through tree-sitter's WASM store (wasmtime), the same mechanism Zed uses for extension grammars. WASM parsing is slower than native, but it runs once per blob at submit time and is cached. Wasmtime is a fixed binary-size cost, paid once instead of per grammar.

Storage: packs are stored in `~/.mergegate/languages/<name>/<version>/`; adding a pack replaces its other versions.

Each release ships the packs built by the same run as release assets, with `languages.json` listing each pack's name, version, file and sha256. The build bakes that index into `mg` (`MG_LANGUAGES_INDEX`), so a binary pins the digests it accepts and packslip's signature covers them. The hub downloads `releases/download/v<its version>/<file>`, at most 64 MB, and installs nothing whose digest differs; a pack ABI change ships as a new mg version. Packs need no signature of their own while they ship only with mg. A build without the index (dev, tests) downloads nothing and installs only `--from`; tests point `MG_LANGUAGES_INDEX` and `MG_LANGUAGES_URL` at a local server.

Detection counts the target branch's files per released pack. `mg project add` asks `--languages <list>|none` when they use packs that aren't installed, defaulting to all of them, and installs them after registering; a failed download is a warning, not a failed add. `mg doctor` warns about packs whose archive isn't the one this mg was released with, and about projects whose files use packs that aren't installed.

```
mg lang list [--available]              Installed languages, or the released ones
mg lang add <name>...                   Download released packs
mg lang add --detect [<project>]        Download the packs a project's files use
mg lang add --from PATH                 Install a pack file, or a directory of them
mg lang update                          Download again packs not from this mg's release
mg lang remove <name>
```

- A file whose language isn't installed renders as plain text, with a hint naming the pack ("No swift language pack").
- Adding a language highlights open items in the background, and open reviews repaint without reloading. Removing one drops its cache entries.

## 7. Slices

| Slice | Responsibility | Port |
|---|---|---|
| Git operations | Staging repos, receive, test-merge, merge, push upstream | `Git` |
| Backend | `github` / `local`: open/update/merge, external comment sync, polling | `Backend` |
| Diff engine | Merge-base diffs, interdiffs (replayed onto the newest base), viewed-state carry-over | in `core`, over `Git` |
| Stacks | Parent links, own-diff base, `parent.*` events, landing order, retargeting | in `core`, over `Git` and `Backend` |
| Comment anchoring | Place earlier revisions' comments onto the one on screen (moved, changed, outdated); move drafts with a review, holding it for flagged ones | in `core`, over `Git` |
| File triage | Pipeline: guards → rules (only stage that can hide) → rankers (agent guide, structural heuristics, judge) | `FileRanker` |
| Inbox prioritization | Explicit priority → conflict pressure and stacked children → age → optional judge | `ItemRanker` |
| Judge | Provider for both rankers | `Judge` |
| Events & delivery | Event log, cursors, debounce, long-poll, `--wake` | in `hub` |
| Identity & transport | Listen modes, Tailscale whois, device trust, `mg connect` | `Tailnet`, `DeviceStore` |
| Highlighting | Language packs, tokenization, cache | `Highlighter` |
| Store | Schema, migrations, attachments | `Store` |
| Design system | Tokens, primitives | `ui/design-system` |
| Agent surface | CLI contract, skill, resume prompt | `cli`, `skill` |

Rules are stored in `rules.toml`. Proposals waiting for approval live in the database and are written to the file only once approved. The hub watches the file and validates hand edits. A hand edit that tightens applies immediately. A hand edit that loosens (moves anything toward `trusted`) is held as a pending proposal until approved in the UI, because the hub can't tell the operator's edit from an agent's. Every rule in effect therefore has the operator's approval.

## 8. Agent surface

1. **Self-describing CLI.** Short `--help`, errors that name the next command, `needs_decision` with options. Output is compact by default, because every byte costs tokens.
2. **Skill embedded in the binary.** `crates/skill` holds the folder and embeds it with `include_str!`; `mg skill install` writes the copy matching that binary, so the skill and the CLI never drift. A test asserts that every command and flag the skill names exists in clap's tree, and that the skill names every command.
3. **`mg resume`** prints a self-contained prompt for agents without skill support.

No MCP server. The CLI works in every harness, while MCP tool schemas cost context in every session.

## 9. Performance budgets (enforced in CI)

| Path | Budget |
|---|---|
| `mg` cold start (`mg --version`) | < 10 ms |
| `mg inbox --json` | < 30 ms |
| UI first paint | < 100 ms |
| Open item (diffs precomputed, comments placed) | < 50 ms |
| Switch file / keyboard action | < 16 ms |
| Scroll a 5k-line diff | 60 fps (virtualized; p95 frame < 25 ms in `ui/tests/review.spec.ts`) |

CI enforces them on Ubuntu (`MG_ENFORCE_BUDGETS=1`); shared macOS runners are too noisy, so there and locally they only report.

The UI also prefetches the next item and next file, and updates optimistically (marking viewed and similar actions don't wait for the server).

## 10. Testing

- Real git repos in temp dirs for git, diff, merge and anchoring tests.
- Golden files for diffs, interdiffs, highlighting spans and triage output.
- A stateful fake GitHub server for the backend (`testkit::FakeGithub`, REST, git over HTTP and a fake `gh`; also the `fake-github` binary for the browser tests); an optional contract test checks it against the real API.
- A fake `tailscale` CLI (`testkit::FakeTailscale`) answering `status` and `whois` from JSON the test writes. `MG_TAILNET_ADDR` puts the hub's tailnet listener on another loopback port, so one machine plays both the hub and a worker.
- Playwright end-to-end tests against a real hub, with state created through `mg` commands rather than a prepared database. Chromium only: the operator uses Chrome and Arc.
- Benchmarks for every budget in §9; a regression fails the build.

## 11. Open questions

- A contract test running `backend-github`'s calls against a scratch repository on real GitHub, opt-in, so the fake can't drift from what GitHub answers.
- The hub holds its store lock across GitHub calls in a submit, merge or abandon, so one slow GitHub call stalls every other request for up to the 30 s timeout. Release the lock around them once that shows up in daily use.
- Staging mirrors one target ref per project, from whichever upstream the backend uses; switching backends re-syncs it from the new upstream, so a `local` item and a `github` item open at once diff against the same target.
- A target renamed to or from a nested name (`release` and `release/1.0`) can't coexist in staging while an open item keeps the old one, and the fetch fails with git's error. Mirror targets under their own ref namespace?
