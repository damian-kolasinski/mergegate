User flows

Every path through mergegate, from first install to merged code. Each flow lists who takes part, where it starts and ends, and the rules that shape it. Flow numbers (F1–F16) are stable IDs, so we can refer to them in later sessions.

You rarely run mg yourself. You ask your agent, it runs the commands, and it asks you when a decision is yours.

Setup

F1

Set up mergegate for a repo

OperatorOperator agentmg CLIHubGitHub
Starts whenYou tell your agent "set up mergegate for this repo".
Ends whenThe agent hands you the UI link and mg doctor passes.
sequenceDiagram
  autonumber
  actor Op as Operator
  participant OA as Operator agent
  participant CLI as mg CLI
  participant Hub
  participant GH as GitHub
  Op->>OA: set up mergegate for this repo
  OA->>CLI: mg hub status
  CLI-->>OA: not running
  OA->>CLI: mg hub start
  CLI->>Hub: start daemon on 127.0.0.1:7800
  OA->>CLI: mg project add .
  CLI-->>OA: needs_decision, backend github or local, target branch
  OA->>Op: GitHub detected. Use GitHub, target main?
  Op-->>OA: yes
  OA->>CLI: mg project add . --backend github --target main
  CLI->>Hub: register project, create staging repo
  Hub->>GH: check credentials and repo access
  alt no GitHub credentials
    Hub-->>OA: needs_decision, log in to GitHub
    OA->>Op: please run gh auth login
    Op-->>OA: done
  end
  opt judge
    OA->>Op: use a model to rank files? none, Jev, Anthropic, local
    Op-->>OA: none for now
  end
  OA->>CLI: mg skill install, mg init, mg doctor
  CLI-->>OA: all checks pass
  OA-->>Op: mergegate ready at http://localhost:7800
  • Commands never prompt. When a decision is needed, the command returns needs_decision with options, and the agent asks you.
  • Everything chosen here can be changed later with a command (F15).
  • Works with no model and no API key. The default judge is none.
  • Logging in to GitHub is the one step you may have to do yourself, because it's interactive.
F2

Connect a worker machine over Tailscale

OperatorOperator agentHubmg CLI (worker)
Starts whenYou tell your agent "let worker-2 submit to my hub".
Ends whenmg doctor passes on the worker.
sequenceDiagram
  autonumber
  actor Op as Operator
  participant OA as Operator agent
  participant Hub as Hub (main machine)
  participant W as Worker (via Tailscale SSH)
  Op->>OA: let worker-2 submit to my hub
  OA->>Hub: mg hub set listen tailnet
  Hub-->>OA: reachable at http://main:7800
  OA->>W: install mg, mg skill install
  OA->>W: mg connect main
  W->>Hub: connect
  Hub->>Hub: Tailscale whois, who is calling?
  alt same Tailscale owner as the hub
    Hub-->>W: trusted
  else another owner
    Hub-->>OA: needs_decision, allow worker-2?
    OA->>Op: allow worker-2 owned by another account?
    Op-->>OA: yes
    OA->>Hub: mg hub allow worker-2
  end
  OA->>W: mg init in each clone, adds remote mergegate
  OA->>W: mg doctor
  W-->>OA: API, auth, git push test all pass
  OA-->>Op: worker-2 connected
  • No tokens to copy. The hub identifies callers through Tailscale, so one agent can do both halves.
  • If your agent can't reach the worker over SSH, an agent on the worker runs the worker half with the same commands.
  • Workers only run the CLI. They need no daemon and no GitHub credentials.
  • Without Tailscale, mg hub token create and mg connect --token are the fallback.
F3

One skill, and how each agent waits

Any agentmg CLIHub
Starts whenAn agent has submitted and needs to wait for feedback.
Ends whenThe agent is woken by an event, having spent as few tokens as its environment allows.
flowchart TD
  S["mergegate skill
SKILL.md, same for every agent"] --> A["mg submit"]
  A --> Q1{"Can I run a command in the background
and be notified when it exits?"}
  Q1 -->|"yes"| B["Run mg wait --timeout 0 in the background"]
  Q1 -->|"no"| Q2{"Can a shell command resume me?"}
  Q2 -->|"yes"| C["mg submit --wake with my resume command
then end the turn"]
  Q2 -->|"no"| D["Loop mg wait --timeout N
N just under my tool time limit"]
  B --> Z1["No tokens while waiting"]
  C --> Z2["No tokens while waiting
hub runs the command on an event"]
  D --> Z3["One short turn per timeout"]
  • One skill for Claude Code, Codex, opencode and Cursor. It asks about capabilities, not agent names, so it works for agents we haven't listed.
  • The skill also covers setup (F1, F2, F15), so the operator never needs a manual.
  • Rules in the skill: never git push or gh pr create. Submit with a guide, a demo and the priority from the brief. Reply to every comment. Judge external feedback critically. Ask the operator on needs_decision.

OperatorOperator agentmg CLIHub

Ends whenThe new setting applies and mg doctor passes.

  Op->>OA: switch this project to plain git

F4

Dispatch work and submit it for review

Operator agentAuthoring agentmg CLIHubGitHubOperator
Starts whenThe operator agent hands a task to an authoring agent.
Ends whenThe item sits in Needs you and the agent is waiting on mg wait.
sequenceDiagram
  autonumber
  participant OA as Operator agent
  participant AA as Authoring agent
  participant CLI as mg CLI
  participant Hub
  participant GH as GitHub
  actor Op as Operator
  OA->>AA: task brief with priority p0 and why
  AA->>AA: implement in its worktree, run tests, self-review
  AA->>CLI: mg submit --guide --attach demo --priority p0 --note
  CLI->>Hub: git push to the hub's staging repo
  CLI->>Hub: register revision r1
  Hub->>Hub: diff against merge-base, sort files into tiers (F12)
  alt github backend
    Hub->>GH: push branch, open PR
    Note over GH: cloud bots start reviewing (F5)
  end
  Hub-->>CLI: item created, revision r1
  AA->>CLI: mg wait
  Hub-->>Op: item appears in Needs you, sorted by priority
  • Submitting again from the same branch adds a revision to the open item instead of creating a new one.
  • Items appear in Needs you right away. External review runs alongside yours, not before it.
  • The guide is the agent's account of what it did: intent, risk areas, suggested file order, and self-review notes.
F5

External review: bots and teammates on GitHub

GitHub (bots, humans)HubAuthoring agentOperator
Starts whenSomeone other than you comments on the PR.
Ends whenEvery comment shows as addressed or rejected in mergegate.
sequenceDiagram
  autonumber
  participant GH as GitHub
  participant Hub
  participant CLI as mg CLI
  participant AA as Authoring agent
  actor Op as Operator
  GH->>GH: Codex bot, Claude bot or a teammate comments
  Hub->>GH: poll PR comments, daemon code, no model
  GH-->>Hub: new comments
  Hub->>Hub: wait 60s for more, then batch them
  Hub-->>CLI: event external.comments
  CLI-->>AA: mg wait returns the batch
  AA->>AA: judge each comment on its merits
  alt comment is valid
    AA->>AA: fix the code
    AA->>CLI: mg reply c1 --status addressed
  else comment is wrong
    AA->>CLI: mg reply c2 --status rejected --body reason
  end
  opt code changed
    AA->>CLI: mg submit, new revision
  end
  Hub-->>Op: each comment shows inline with its status
  AA->>CLI: mg wait again
  • The hub polls GitHub itself. It's plain code in the daemon, so polling costs no tokens. The agent only spends tokens when mg wait returns with something to do (F3).
  • Replies stay in mergegate. Nothing is posted back to the GitHub thread.
  • Your job here is to audit the agent's verdicts, not to redo the bots' review. You can override any rejection (F6).
  • Local-backend projects have no PR, so this flow doesn't happen for them.

OperatorHubAuthoring agent
Starts whenYou submit Request changes.
Ends whenThe new revision is back in Needs you, showing only what changed.
sequenceDiagram
  autonumber
  actor Op as Operator
  participant Hub
  participant CLI as mg CLI
  participant AA as Authoring agent
  Op->>Hub: Request changes, 3 comments
  Hub-->>CLI: event review.submitted
  CLI-->>AA: mg wait returns your review
  AA->>AA: fix the code
  AA->>CLI: mg reply per comment, addressed or rejected with reason
  AA->>CLI: mg submit, revision r2

F8

Approve and merge

OperatorHubGitHub or Operator repoAuthoring agentOperator agent
Starts whenYou press Approve and merge.
Ends whenThe code is on the target branch and the operator agent knows.
sequenceDiagram
  autonumber
  actor Op as Operator
  participant Hub
  participant GH as GitHub
  participant Repo as Operator repo
  participant AA as Authoring agent
  participant OA as Operator agent
  Op->>Hub: Approve and merge
  alt github backend
    Hub->>GH: merge PR via API
    GH-->>Hub: merged
  else local backend
    Hub->>Hub: merge in staging repo
    Hub->>Repo: push to target branch, update checkout if clean
    alt checkout clean or target not checked out
      Repo-->>Hub: target updated
    else uncommitted changes on target
      Repo-->>Hub: rejected
      Hub-->>Op: held in Merging, says why
      Op->>Repo: commit or stash
      Op->>Hub: Retry
    end
  end
  Hub-->>AA: mg wait exits with code 3, item merged
  AA->>AA: clean up its worktree
  Hub-->>OA: mg events --follow reports item.merged
  OA->>OA: dispatch work that was waiting on this
  Hub->>Hub: test-merge every other open item (F9)
  • There's no CI to wait for, so approving merges right away.
  • Nothing is ever force-pushed or overwritten in your checkout.
  • Workers get the new target with git fetch mergegate.
F9

Merge conflicts

HubAuthoring agentOperator
Starts whenThe target branch moves, or a merge fails.
Ends whenThe agent submits a revision that merges cleanly.
sequenceDiagram
  autonumber
  participant Hub
  participant CLI as mg CLI
  participant AA as Authoring agent
  actor Op as Operator
  Hub->>Hub: target moved, test-merge every open item
  Hub->>Hub: item 45 conflicts with the new target
  Hub-->>Op: badge "conflict, with agent" on item 45
  Hub-->>CLI: event merge.conflict
  CLI-->>AA: mg wait returns the conflict
  AA->>CLI: git fetch mergegate
  AA->>AA: rebase, resolve, run tests
  AA->>CLI: mg submit, new revision
  Hub->>Hub: test-merge clean
  Hub-->>Op: item 45 back in Needs you
  • Conflicts go to the agent, not to you. You usually only see the badge.
  • The hub also tests open items against each other. "Conflicts with item 45" in the inbox tells you which item to merge first.
F16

Stacked items

Authoring agentmg CLIHubOperator
Starts whenAn agent's work is too big for one review and it splits it.
Ends whenEvery item in the stack is merged, bottom first.
sequenceDiagram
  autonumber
  participant AA as Authoring agent
  participant CLI as mg CLI
  participant Hub
  actor Op as Operator
  AA->>CLI: mg submit, the bottom part
  CLI-->>AA: item 41
  AA->>CLI: mg submit --on 41, the next part
  CLI-->>AA: item 42, stacked on 41
  Hub-->>Op: inbox shows 41 with 42 under it
  Op->>Hub: Request changes on 41
  AA->>CLI: mg submit, 41 r2
  Hub-->>CLI: event parent.updated for 42
  CLI-->>AA: mg wait returns, with the rebase command
  AA->>AA: rebase 42 onto 41 r2, resolve if needed
  AA->>CLI: mg submit, 42 r2
  Hub->>Hub: own diff of 42 unchanged, viewed marks kept
  Op->>Hub: Approve 42 (merge after 41)
  Hub-->>Op: 42 waits in Merging for 41
  Op->>Hub: Approve and merge 41
  Hub->>Hub: merge 41, retarget 42 to the target
  Hub->>Hub: merge 42
  • Each item shows only its own changes, against the parent revision it is built on.
  • The hub never writes to an item's branch. The agent rebases with the command the event gives it, and submits.
  • Viewed marks and an approval survive a rebase only where the own diff is unchanged.
  • If 41 lands by squash, 42 gets parent.updated and is rebased onto the target before it merges.
  • If 41 is abandoned, 42 goes back to its agent with parent.abandoned, and the agent moves it with mg submit --on.

Prioritize the inbox

Operator agentAuthoring agentOperatorHub
Starts whenThe operator agent dispatches work, or the plan changes.
Ends whenThe inbox shows items in the order that unblocks the most work.
sequenceDiagram
  autonumber
  participant OA as Operator agent
  participant AA as Authoring agent
  participant Hub
  actor Op as Operator
  OA->>AA: brief says p0, blocks the auth refactor
  AA->>Hub: mg submit --priority p0 --note "blocks auth refactor"
  Hub-->>Op: item at the top of Needs you, note shown
  Note over OA: later, the plan changes
  OA->>Hub: mg prioritize item 42 --priority p2 --note "auth refactor postponed"
  Hub-->>Op: inbox reorders
  Op->>Hub: press p on an item to set priority by hand
  Hub-->>Op: the latest change wins
  • Sort order: priority, then how much merging it unblocks (conflict pressure), then age.
  • Each row shows the size of its Review tier, the real cost of the item, not its total line count.
F11

An agent proposes a triage rule

Any agentHubOperator
Starts whenAn agent runs mg rules propose.
Ends whenThe rule is active, or you rejected it.
flowchart TD
  A["mg rules propose
path, diff match, tier, reason"] --> B{"Does it show you more or less?"}
  B -->|"more: toward Review"| C["Active immediately"]
  B -->|"less: toward Trusted"| D["Pending approval"]
  D --> E["Inbox badge: 1 rule to approve"]
  E --> F["Preview: past files this rule would have hidden"]
  F --> G{"Your call"}
  G -->|"Approve"| C
  G -->|"Reject"| H["Discarded, proposer can see it with mg rules show"]
  C --> I["Open items are re-sorted into tiers"]
  • Rules can match on file paths and on what changed. Example: SwiftUI views are trusted unless the diff touches NavigationStack or @State.
  • Rules are personal, stored on your hub, and editable by hand.
F12

How a file gets its tier

HubJudge (optional)
Starts whenA revision is submitted, or the rules change.
Ends whenEvery changed file is in Review, ordered by importance, or in Trusted, each with a reason.
flowchart TD
  A["Changed file"] --> B{"Built-in guard?
rules file, or you commented on it before"}
  B -->|"yes"| R["Review"]
  B -->|"no"| C{"Matches a rule?
first match wins"}
  C -->|"yes"| D["Tier from the rule"]
  C -->|"no"| R
  D --> E["Agent guide and judge"]
  R --> E
  E --> F["Order files within Review, add reasons and flags"]
  E --> G["Can promote a Trusted file to Review
when its content looks risky"]
  E -.->|"never"| T["Trusted"]

Only your rules can hide a file. The authoring agent grades its own work and the judge can be wrong, so neither can ever move a file into Trusted.
